# SecureVault - Security Review: Need to Fix

Review date: May 15, 2026
Scope: All Java/Spring Boot backend source, configs, DB migrations, Docker/deploy files

---

## 🔴 CRITICAL

### 1. 2FA setup is completely broken — can never be enabled

**Files**: `TwoFactorController.java:82`, `TwoFactorAuthService.java:111-121`, `Enable2FARequest.java`

`enable2FA()` is called with `secret=null`. The `verifyCode()` check looks up the user's stored TOTP secret (which is `null` at setup time → returns `false` → throws "Invalid verification code"). Even if it passed, it would store `null` as the secret. `Enable2FARequest` has no `secret` field — the secret generated by `/setup` is never passed back to `/enable`.

**Fix**: Add a `secret` field to `Enable2FARequest`, pass it to `enable2FA()`, and verify the code against the provided secret instead of the stored secret.

---

### 2. TOTP secret stored in plaintext in database

**File**: `User.java:80-81`

`twoFactorSecret` is stored unencrypted. DB compromise → attackers can generate valid TOTP codes for any user.

**Fix**: Encrypt the TOTP secret at rest using AES-256-GCM with a server-side key.

---

## 🟡 HIGH

### 3. Hardcoded production secrets in docker-compose.yaml

**File**: `docker-compose.yaml:17-21,36,50`

DB password (`mg8Jn^#Cpe`), JWT secret, and Redis password hardcoded in plaintext and committed to git. Anyone with repo access gets all production credentials.

**Fix**: Use environment variables. Remove secrets from version control.

---

### 4. Failed logins are never audit-logged

**File**: `AuditService.java:106`, `AuthController.java:88-101`

`auditService.logFailedLogin()` is defined but never called anywhere. Failed login attempts leave zero trace in the audit log. Brute-force attacks are invisible.

**Fix**: Call `auditService.logFailedLogin()` from the controller catch path or `AuthService.login()` before the exception propagates.

---

### 5. Weak/guessable default JWT secret fallback

**Files**: `.env:11`, `application.properties:20`, `application-prod.properties:20`

The secret `SecureVaultSecretKeyForJWTTokenGeneration2024` is not cryptographically random. Both `application.properties` and `application-prod.properties` fall back to this string if `JWT_SECRET` env var is not set. The `.env` file also uses this value.

**Fix**: Remove fallback defaults. Validate at startup that `JWT_SECRET` is at least 32 bytes. Generate using `openssl rand -base64 32`.

---

## 🟠 MEDIUM

### 6. `.env` not in `.gitignore`

**File**: `.gitignore`

`.env` is untracked but NOT ignored. It appears under "Untracked files" in `git status`, not under `.gitignore`. One `git add .` and all secrets are committed.

**Fix**: Add `.env` to `.gitignore`.

---

### 7. In-memory rate limiting resets on restart

**Files**: `LoginRateLimiter.java`, `RateLimitingFilter.java`

Both use `ConcurrentHashMap` — all state lost on server restart. Attackers can trigger a restart then brute-force.

**Fix**: Use Redis (already in the dependency stack) for persistent rate limit state.

---

### 8. X-Forwarded-For spoofing bypasses rate limiting

**File**: `RateLimitingFilter.java:53-58`

`X-Forwarded-For` is trusted without validation. Attackers can spoof IPs to bypass per-IP rate limits.

**Fix**: Only trust `X-Forwarded-For` when the request comes from a known reverse proxy.

---

### 9. Vault audit logs missing IP and User-Agent

**File**: `VaultController.java:69,108,131,151,169`

Every `auditService.logVaultAccess()` call passes `null, null` for IP and User-Agent. All vault CRUD audit entries are missing the most critical forensic data.

**Fix**: Pass `httpRequest.getRemoteAddr()` and `httpRequest.getHeader("User-Agent")` to all vault audit log calls.

---

### 10. No size limits on vault entry payloads

**File**: `VaultEntryRequest.java`

`encryptedData` and `iv` have `@NotBlank` but no `@Size` constraint. Storage exhaustion attack possible.

**Fix**: Add `@Size(max = ...)` constraints on both fields.

---

### 11. SSL/TLS not enforced

**Files**: `.env:17`, `application.properties:34`, `application-prod.properties:34`

`REQUIRE_SSL=false` and `server.ssl.enabled=${SSL_ENABLED:false}`. Credentials travel in plaintext unless a reverse proxy handles TLS.

**Fix**: Set `REQUIRE_SSL=true` in `.env.example` as documented production expectation. Ensure reverse proxy enforces HTTPS.

---

### 12. Swagger enabled in `.env` defaults

**File**: `.env:18`

`SWAGGER_ENABLED=true` in the checked-in `.env` file. Risk of deploying with API docs publicly exposed.

**Fix**: Set `SWAGGER_ENABLED=false` in `.env`. Enable only in development profiles.

---

### 13. Empty default DB password

**Files**: `application.properties:6`, `application-prod.properties:6`

`spring.datasource.password=${DB_PASSWORD:}` — defaults to empty string if env var not set. Username defaults to `tanay`.

**Fix**: Remove empty default, or add startup check that fails if `DB_PASSWORD` is not set.

---

### 14. Password change endpoint lacks rate limiting

**File**: `AuthController.java:163`

`/change-password` has no rate limiting. A compromised JWT allows unlimited current-password guessing.

**Fix**: Apply rate limiting keyed by user ID.

---

### 15. No JWT revocation mechanism

**File**: `JwtTokenProvider.java`

Leaked tokens stay valid until expiration (1 hour default for access, 1 day for refresh). No blacklist or token versioning exists.

**Fix**: Consider a Redis-based token blacklist for immediate revocation.

---

### 16. No 2FA enforcement on sensitive operations

**Scope**: All controllers

Once a user logs in, password changes, device registration, and vault access have no 2FA re-verification. If a JWT is stolen, 2FA provides no additional protection.

**Fix**: Require TOTP re-verification for sensitive operations (password change, disable 2FA, new device registration).

---
